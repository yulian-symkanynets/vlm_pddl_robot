HEKATE Planner API

The planning server for the Lite 6 sorting robot. The laptop sends what it sees (a scene in JSON, or a photo) and a task in words; the server returns pick and place steps that are checked on the scene and proven shortest.

1Overview

The laptop calls the server only for situations it cannot solve by itself: objects stacked on each other, a task it does not know, or a scene that changed. Every answer is a list of high-level steps the robot executes deterministically. Motion planning stays on the robot side.

scene JSON or photo→understand task (model)→planning problem→plan + proof→check on the scene→steps
0.68 splan for 16 objects (example below), no model needed for the scene
1.4 kBthat scene as JSON, against 387 kB for its photo
16 of 16moves, proven shortest: every object that must move moves once
0 callsto the model when replanning from a new scene JSON

2Quick start

Is it up?

curl http://192.168.73.15:8010/health

Plan from a scene file

curl -s http://192.168.73.15:8010/plan \
     -H 'Content-Type: application/json' \
     --data-binary @examples/requests/15_four_towers_sort.json

From Python (the laptop)

import requests
URL = "http://192.168.73.15:8010"

r = requests.post(f"{URL}/plan", json={
    "instruction": "Sort the objects by colour into the zones.",
    "scene": scene,                     # see section 3
}).json()

if r["status"] == "ok":
    for step in r["plan"]:
        print(step["action"], step["args"])     # pick-from-item ['blue_block_2', 'green_cube_1'] ...
    print("shortest:", r["quality"]["optimal"])
else:
    print(r["status"], r["message"])            # clarify / need_observation / no_plan / error

3Scene JSON

The scene says which objects exist, what each one stands on, and where objects may be put. Positions in millimetres are not needed: the planner works with "what stands on what", and the robot finds the exact poses itself.

Objects

FieldRequiredMeaning
idyesUnique name, e.g. red_block_2. Letters, digits, underscores.
onyesWhat it stands on: table, another object's id, or a zone id. unknown if the camera cannot tell.
colorrecommendedred, yellow, blue, green, … Used to understand "the red ones".
shaperecommendedcube, block, bar, cylinder, prism, … Nothing can be put on a prism.
labelnoFree description shown to the model. Default: color + shape.
height_mmnoNeeded for height limits (shelves, max_height_mm).
size_mmnoFootprint (also width_mm, diameter_mm). When given, a larger object is never put on a smaller one.

Places (zones or places)

FieldMeaning
ide.g. red_zone. The open table is always available and is not a place.
colorColour of the paper, used for "sort by colour".
capacityHow many objects fit directly on it. Objects stacked on top of each other inside a zone do not count as "in the zone".
kindzone (default), box, tray, bin, shelf. A box may have "open": false.
max_height_mmA tower standing in this place may not be taller (sum of height_mm).
max_top / max_objectsAt most this many objects in one tower in this place.

Optional "rules" for the whole scene: {"max_height_mm": 250, "max_objects": 4, "no_larger_on_smaller": true}. They apply to every tower, also on the table, and while the plan runs, not only at the end. With limits, plans come from the general search; impossible limits are explained at once.

Several objects of one colour

Allowed and common: four red objects with different shapes are four objects. Give each its own id (red_block_1, red_block_2, red_bar_1, …). If two objects arrive with the same id, the server renames the second (red_block_2) and decides "on red_block" by physics: at most one object on another, no loops. When both readings are possible it does not guess and answers need_observation.

Other accepted forms

  • A support map instead of on: "support": {"red_block_1": "yellow_block_1", ...}
  • Relations: "relations": [{"subject": "a", "relation": "on", "object": "b"}]
  • "hidden": ["id", ...] for objects that are visible but not localised well enough to grasp: the plan then starts with an observe step.

4Tasks: instruction, goal, constraints

Normally you send the task in words (instruction, any language the model understands). The model turns it into goal facts and constraints; the response shows what it understood in goal and constraints. You can also send them yourself, which skips the model call.

Goal entryMeans
{"object": "a", "in": "red_zone"}a ends directly in the zone
{"object": "a", "on": "b"}a ends directly on b (a tower is several entries)
{"object": "a", "on": "table"}a ends on the open table
{"sort_by_color": true}every object into the zone of its own colour; the server expands it, and an explicit entry for one object overrides it
{"stack_in_zones": true}one tower per colour, standing in the zone of that colour; works with no_table and limits. Four towers of 16 objects without the table: 16 moves, proven shortest, about 1.8 s
{"stack_by_color": true}one stack per colour on the table; the planner chooses which object is the base and the order, for the fewest moves (four towers: 15 moves, proven shortest, about 1 s). Send it alone, without constraints
ConstraintMeansSaid as
"no_table": truenothing may be put down on the table"don't use the table"
"keep": ["a"]these objects must not be moved"leave the blue cube"
"never_on": [["*", "b"]]never place the first on the second"never put anything on the red bar"
"first": ["a"]this object moves before anything else"start with the green cube"

A constraint is kept only if the model quotes words that really are in the instruction, so the model cannot invent restrictions.

Any other goal: a formula

When no entry above fits, the model writes one {"formula": F} that says what must be true at the end. The server checks it (an unknown name or a wrong type gives an exact message and the model is asked again), expands forall / exists for the objects of the scene, searches for moves and verifies the plan twice: every action on the robot's domain, and the formula on the final arrangement. The response repeats the formula in plain words (goal[0].in_words).

PartWritten as
combine{"and": [F, ...]} {"or": [F, ...]} {"not": F} {"imply": [F, F]}
quantify{"forall": {"x": "object"}, "where": F, "body": F} and {"exists": {"p": "place"}, "where": F, "body": F}
arrangement{"on": [x, y]} directly on · {"on_table": [x]} · {"in": [x, place]} · {"clear": [x]} nothing on it · {"above": [x, y]} somewhere above in a stack
fixed facts{"color": [x, "red"]} · {"shape": [x, "cube"]} · {"same_color": [x, y]} · {"same_shape": [x, y]} · {"is": [x, y]}
"all cubes into the red zone":
{"goal": [{"formula": {"forall": {"x": "object"},
                       "where": {"shape": ["x", "cube"]},
                       "body":  {"in": ["x", "red_zone"]}}}]}

You can send such a goal yourself: examples/requests/18_formula_cubes_to_red_zone.json. Measured on the 16-object scene: "every stack one colour" written as a formula plans in about 1.3 s with 20 moves (the exact shortcut stack_by_color needs 15, proven shortest). The plan is verified but not proven shortest; the search keeps the best plan found within 8 s and says no_plan after that, because it cannot tell "impossible" from "not found yet". The robot's actions limit what a goal can ask for: only what stands on what, not positions or rotations.

Send scene (preferred) or images_b64. With a scene, no image is read and only the goal is asked from the model.

POST/plan/upload

Multipart form, handy from the command line. Fields: instruction (required), files (one or more images) or scene (JSON text), resolution, crop (JSON text), planner, attempts.

curl -s http://192.168.73.15:8010/plan/upload \
     -F instruction='Sort the objects by colour into the zones.' \
     -F files=@towers.jpg -F resolution=medium

POST/replan

The scene changed: the robot made progress, a step failed, or a person moved something. Reuses the goal already understood; the model is not called.

{"request_id": "20261120_101512_ab12cd",   // from the /plan answer (or the last /replan)
 "scene": { ...the scene as it is NOW... }}

Answer: like /plan, plus decision (kept or replanned), changes and, when kept, done_actions.

Failed step: add "failed": ["(place-on-table b1)"] (or [{"action": ..., "args": [...]}], or [{"step": 2}] from the previous plan). A failed place becomes never_on [object, target], a failed pick keeps the object where it is; they are added to constraints, so they also hold for every later replan, and failed_rules says what was excluded.

POST/solve

Planner only: {"scene": {...}, "goal": [...], "constraints": {...}, "ordered": false, "compact": false}. Constraints work here exactly as in /plan.

POST/perceive

Form with files (and optional resolution, crop). Returns scene: what the model sees. Use it to check perception before planning.

POST/camera/plan · /camera/replan

scripts/camera_client.py streams a camera with POST /stream/{cam} (one JPEG per request). Then /camera/plan takes {"camera_id": "cam0", "instruction": "..."} and /camera/replan takes {"camera_id": "cam0", "request_id": "..."}, both with optional resolution, crop, max_age_s (default 5 s). Live view: GET /stream/{cam}.mjpg; list: GET /streams.

GET/health · /requests/{id} · /memory · /dashboard

  • /health: model, quantization, uptime, number of requests.
  • /requests/{id}: the logged request and answer (also on disk in logs/requests/<id>/).
  • /memory: what the experience database holds. POST /memory/clear?kind=goal empties one kind (scene, goal, plan) or all.
  • /dashboard?last=50: graphs of time per request and stage, database hits, resolution, outcomes.
  • /domain: the fixed PDDL domain. /examples: example cases for the test page.

FieldMeaning

timingsperceive_s (image to scene), goal_s (instruction to goal), plan_s, total_s, in seconds

The example is the measured answer of /solve for the four-tower scene, which needs no model. With an instruction, timings also contains goal_s, and with a photo perceive_s; with the database on, memory is added.

7Replanning

  • After every move (or when something looks different), send the new scene to /replan with the newest request_id.
  • kept: the scene is one the old plan passes through. The rest of the plan comes back, still proven shortest.
  • replanned: anything else. A new plan from the new scene, same goal and constraints, in about 0.15 s, without the model.
  • A failed grasp leaves the scene unchanged, so the same step comes back: an automatic retry.
  • A new object on top is cleared first. If an object the task needs is gone, the answer is clarify.

10Network

The server runs in WSL on HEKATE; Windows forwards port 8010 to it. WSL gets a new internal address after a restart, so the forwarding is redone then. In a normal PowerShell, read the address:

(wsl hostname -I).Trim().Split(' ')[0]

Then in PowerShell as Administrator, with that address:

$ip = '172.30.191.115'        # the address you just read; it changes after a restart
netsh interface portproxy delete v4tov4 listenaddress=0.0.0.0 listenport=8010
netsh interface portproxy add v4tov4 listenaddress=0.0.0.0 listenport=8010 connectaddress=$ip connectport=8010
netsh interface portproxy show v4tov4

The firewall rule "WSL planner 8010" stays. Start the server in WSL with ./serve.sh start qwen3-vl-8b 4bit (or qwen3-vl-2b bf16 for speed).

11Open points

  • Model times in this page are not measured yet on HEKATE; /dashboard shows them once requests run.
  • The faster models (Qwen3-VL-2B, Qwen3.5, LFM2.5-VL) are configured but not yet compared: scripts/compare_models.sh.
  • A step is only excluded when the robot reports it in failed; without that, a grasp that keeps failing comes back.
  • "Shortest" counts pick and place moves for the scene as understood; arm travel distance is not part of it.
  • A scene sent while an object is held in the gripper cannot be described; send scenes between moves.
